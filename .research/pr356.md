# DeepSeek: cache conversations across switches and restarts, so sub-agents don't re-read prompts (first token up to 7x faster)

## Why

maya-ds4 holds one conversation: a prompt that continues it reuses its state, anything else starts over. An agent
runtime runs a parent and three workers on one slot, and their prompts alternate between ~70k and ~185k tokens. In
one agent runtime's engine log (the 632 `prompt` lines as of 2026-10-21 14:59; the engine was still serving), 257 read
their prompt from token 0 - 142 of them longer than 30k tokens, and those read at ~930 tok/s: a 70k-token prompt takes
~75 s and a 185k one ~200 s, every switch. Every one of the log's 375 reuses continued the conversation's whole state
in place (none went back to a checkpoint), so a slot taken only when its whole state is a prefix of the prompt fits
the traffic. The GLM engine already solves this (`STRATA_GLM_SLOT_KEEP`): a conversation that loses the model is set
aside, and a request that continues it takes it back. This ports that to the DeepSeek engine.

## What

`src/ds4/ds4_model.{hpp,cu}` - the state of a conversation out of the model and back:

- `Model::slot_save(out, err)` / `Model::slot_load(data, bytes, n_pos, err)`: the whole state, as one byte string -
  the position, its tokens, every layer's 128-token window ring (the three DSpark blocks' included), the
  compressors' partial groups, and each KV source's compressed KV (FP4) and index keys (FP4, one row a completed
  group: `0 .. pos / ratio`; the group the position has not completed yet lives in the partial group). A tensor
  parallel group's members hold the same state, so one member's ring is saved and written back into all of them.
  The Engram n-gram history (`ctoks`) is rebuilt from the tokens at load (a slot never holds a picture, so its rows
  are the tokens' `eg_map` rows).
- `Model::slot_identity()` - what a saved conversation must match: the engine's version, the geometry (dim, hd, win,
  compress ratios, KV and index sources), whether the DSpark blocks are loaded, and the pack's files (sizes).
- A state unchanged since it was saved refuses to save again ("it is already set aside"); every feed, rollback,
  reset and restore clears that, so a duplicate is never written. A load that stops part-way (a damaged file whose
  size still matches) resets the state rather than serving one made of two conversations.

`src/ds4/ds4_main.cpp` - the slots themselves, as the GLM driver has them:

- a request that does not continue the conversation in the model sets it aside *first* (otherwise its state is lost),
  then takes back the kept conversation whose tokens are the longest prefix of the prompt (past the checkpoint the
  model already holds, so a shorter slot never wins over a longer in-process restore); a prompt with pictures takes
  none back, and a conversation that holds pictures is not set aside (text only, as the GLM slots). A fresh engine
  holds 0 tokens, which no prompt continues - every restart's first request is this case - so it takes the folder's
  conversation rather than reading from token 0.
- `MAYA_DS4_SLOT_KEEP=1` turns it on and keeps the conversations across runs; default off, so the engine is unchanged
  unless asked.
- `MAYA_DS4_SLOT_CAP` (4): conversations kept in RAM; past it the least recently used is written to the folder and
  read back from there - RAM first, the folder past the cap. `MAYA_DS4_SLOT_DIR` (`<pack>/slots`),
  `MAYA_DS4_SLOT_MIN` (1024), `MAYA_DS4_SLOT_DAYS` (7).
- `MAYA_DS4_SLOT_GB` (16) caps the folder's `.bin` files, counted at start and after every write: while they are over
  it the folder's least recently used conversation is removed - never the one just written, so a conversation bigger
  than the cap stays. The `.meta` beside each is a few KB and is not counted.
- a slot is a `.bin` (the state) and a `.meta` (this model's identity, the tokens, the size), both written under a
  temporary name first; at start the folder is indexed and a slot is removed when its `.meta` is missing, foreign,
  disagrees with its file, or is older than `_DAYS`. A file write needs 8 GB free (the GLM engine's guard).
- QUIT (or the end of the engine's input) sets aside the conversation in the model and writes every conversation in
  RAM to the folder, so the next run reads on from them; `SIGTERM`/`SIGINT`/`SIGPIPE` are ignored while serving so a
  supervisor's group-kill cannot end it mid-write (only with the slots on).
- v1.1.20's `STOP` during a long prompt does not leave the state part-way through the prompt: it goes back to the
  state the prompt started from (a checkpoint taken before it) and, when there was none - a prompt read from token 0
  - resets the model. So `slot_put` always sees `tokens()` as long as the position; `slot_save` also refuses a state
  whose tokens do not add up (`the state's tokens do not match its position`), so one whose feed left them apart could
  never be written to a slot.

`docs/SETTINGS.md` - "DeepSeek: conversations kept", with the settings table.

State sizes (DeepSeek-V4.1-Flash, 524288 context): ~65 MB for a 70k-token conversation, ~170 MB for 185k (the four
sources' compressed rows are ~155 MB of it; the 43 window rings 2.9 MB). A save is a device-to-host copy plus a
folder write; a take is the same the other way - 0.1-0.5 s against 75-200 s of re-reading.

## Proof

`tools/ds4/slot_keep_test.py` (needs the GPUs free; it starts the engine itself, six times):

```
python tools/ds4/slot_keep_test.py --pack <pack>/maya-ds4
```

The prompts are real text - the repo's `tools/tokenizer_corpus.txt`, tokenized through the pack's tokenizer - not
random token ids: random ids sit where the logits are near-ties, and two greedy runs print different tokens, so
nothing can be compared. A and B open with different text (they diverge at token 2), so B's request cannot reuse
A's state in place.

- **no-keep, the reference** (`MAYA_DS4_SLOT_KEEP=0`): A (12k tokens), B (9k), then A's next turn (A + its answer +
  64 new tokens), one process: the turn reports `reused` 0. Its answer to A builds the turn, and every later run
  sends those same bytes, so all six runs send byte-identical prompts.
- **no-keep, a second process**: the same prompts once more - the engine's own run-to-run prompt path, measured
  rather than assumed. When the two reads agree (the expected case with real text), the greedy check claims
  identity; when they do not, the script prints that the engine's prompt path is not run-to-run deterministic and
  compares the slot runs against both reads instead of claiming either.
- **in-run**: A, B, A's next turn, one process: the third request reports `reused` = A's full prefix (A and all but
  its answer's last fed token), the prompt's length agrees, and A's own answer matches the reference's.
- **kept**: A, B, QUIT: the folder holds 2 `.bin` and 2 `.meta`, both conversations, and stays under a 0.05 GB
  `MAYA_DS4_SLOT_GB`.
- **restart**: A's next turn alone in a new process: the same `reused`, from the folder (the start's NOTE line says 2
  conversations were kept from the earlier run). This is the case a fresh engine is in - 0 tokens in the model - so
  it is the one that must take the folder's slot back, not "continue" its own empty state from token 0.
- **evict**: A, B, C (4k tokens) into a folder capped at the measured A+B bytes, so three conversations cannot fit:
  the least recently used (A) is gone, B and C stay, and the folder is under the cap.
- **greedy**, `spec=0` on purpose: the slot runs print the reference's tokens; if the two no-keep reads differ,
  one of the two reads' tokens (see above).

`spec=0` is deliberate: with the drafter a request's state can end a few tokens past its last *printed* one (a draft
accepted before `max_new` cut it), and the next prompt - which carries only the printed answer - would then not be a
prefix of the state, so the slot would (correctly) not be taken and the count would say so. That is a property of the
engine's existing reuse too ("a stop within accepted drafts leaves the state past it"), not of a slot; a follow-up
could save the state at the printed prefix instead (a checkpoint before the last round's feed).

Built here on v1.1.20 (`origin/main`, 35bb2b2) with
`cmake -S . -B build -DCMAKE_BUILD_TYPE=Release -DSTRATA_ENABLE_CUDA=ON -DCMAKE_CUDA_ARCHITECTURES="86;120"` and
`cmake --build build --target maya-ds4`. The test was then run on 2x RTX 5090 + RTX 3090 (Maya-S): 14 of 14
checks passed - the numbers are in Measured.

Note on the token check: a restored state and a full re-read do not produce bit-identical arithmetic (chunk boundaries
differ; `tools/ds4/bytecheck.sh` documents the same for checkpoints) - the check is the greedy tokens, as asked, not
the logits.

## Measured

`tools/ds4/slot_keep_test.py` on 2x RTX 5090 + RTX 3090 (`--gpus 0,2,1`), Maya-S, v1.1.20 + this branch:
**14 of 14 checks passed**.

- **prompt path, run to run**: the two no-keep runs printed the same 24 greedy tokens - A's answer and the turn; the
  slot runs' tokens were the reference's.
- **in-run switch**: A's next turn (12,088 tokens) reused 12,023 of 12,023 tokens - 3.5 s against 21 s for the same
  read without slots; the answer was the reference's.
- **restart from the folder**: a fresh process took A's conversation from the folder and reused 12,023 of 12,023 in
  3.8 s; its tokens were the reference's. The folder held A and B: 24.1 MiB, under `MAYA_DS4_SLOT_GB=0.05`.
- **eviction**: A, B and C into a 24.1 MiB cap: the least recently used (A) was removed, B and C kept - 17.1 MiB.

## Also verified

A tester ran `tools/ds4/slot_keep_test.py` on a Strix Halo (Ryzen AI Max, 128 GB of unified memory) and the suite
passed there: **in-run reused 12,023 of 12,023 tokens in 37 s** (64 s for the same read without slots),
**restart from the folder reused 12,023 in 31 s**, the eviction case passed, the greedy tokens were identical, and
slots on against off cost no decode speed. Three findings from that run, none of them a bug in the slots:

- **`MAYA_DS4_KEEP_THINKING` (off, DeepSeek's own serving).** Through the server, a tool-less chat never took a slot
  back: the frontend renders with the reference encoder's `drop_thinking` (an earlier turn's reasoning is dropped at
  the next user turn), so every turn renders a history that differs at each assistant turn and the next turn continues
  nothing - their case, a 4,215-token follow-up behind a 4,197-token state it did not contain, read in 19.3 s. With
  the setting on, A2 after B1 **reused 4,197 of 4,215 and read in 2.7 s**. Requests that carry tools keep their
  thinking already (`serve/ds41_encoding.py`), which is why agent traffic reused fine; a tool-less chat needs both
  settings. The setting is one the server reads, so it is in `SERVER_ENV` (a config's `env` reaches it as the other
  rows of that table do), and its row sits beside `MAYA_DS4_SLOT_KEEP`'s in `docs/SETTINGS.md`.
- **the client's side, docs.** Each assistant turn goes back with its `reasoning_content`, as it came: from `content`
  alone the prompt differs from the state the slot holds and nothing is reused, with no error and no log line. One
  line in the same section.
- **`tools/ds4/slot_keep_test.py --config <maya-ds4.json>`.** The script started the engine without a config's
  environment, so on that APU the engine sized its pool from hipMemGetInfo (125 GB of a 128 GB box) and the first QUIT
  hung its 300 s; `DS4_POOL_GB=88` fixed it. The config's DeepSeek settings (`DS4_*` and the `MAYA_DS4_*` names, under
  the names the engine reads) now go to the engine, the test's own slot settings over them, and the usage text says
  so. Its tokenizer import moved into `main()`, so the new host-side test (`tools/test_slot_keep.py`) reads the
  config's settings without `regex`.

Both settings are checkable without a GPU: `python -m unittest serve.test_ds41_conformance tools.test_slot_keep`
(the conformance suite's two new cases render the prompt with the setting on and off, and require the next turn's
prompt to start with the one the state holds).
